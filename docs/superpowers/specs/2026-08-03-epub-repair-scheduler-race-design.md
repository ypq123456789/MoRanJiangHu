# EPUB 修复与后台任务竞态修复设计

## 问题

当前 `小说拆分后台调度服务.stop()` 只停止后续扫描，不等待正在执行的拆分请求结束。EPUB 修复写入 832 章后，旧执行器仍可能用内存中的 1081 章数据收尾落盘，覆盖修复结果。界面因此显示“修复完成”，实际数据随后恢复为旧章节与旧分段。

## 目标

- EPUB 修复写入前，确保当前拆分执行器已经完成中断收尾。
- 等待结束后重新读取数据集与任务，避免使用修复确认前的陈旧 React 状态。
- 修复结果落盘后才允许后台调度重新启动。
- EPUB 解析期间提供明确的忙碌提示，并阻止重复提交。
- 不改变已有分段保留、受影响分段重排和自动续跑算法。

## 方案

为小说拆分调度器增加异步 `waitForIdle()` 能力。调用方先执行 `stop()` 并请求中断目标任务，再等待调度器从 `busy=true` 变为 `busy=false`。等待支持最大时限，超时则中止修复并显示错误，不允许在旧任务仍可能写入时继续保存。

用户确认修复后，流程调整为：

1. 停止后台调度并请求中断当前数据集的运行任务。
2. 等待当前执行器完成中断、数据集回写、快照刷新和任务状态更新。
3. 从存储重新读取目标数据集和完整任务列表。
4. 基于最新数据重新计算 EPUB 修复结果。
5. 依次保存修复后的数据集、任务和注入快照。
6. 仅当后台运行设置开启且存在待处理分段时，重新启动调度器。

解析文件开始后显示“正在解析 EPUB”忙碌状态；确认框出现或解析失败时清除该状态。修复等待与保存期间继续显示对应阶段，按钮保持禁用，避免重复执行。

## 错误处理

- EPUB 解析失败：清除忙碌状态，保留原数据并显示解析错误。
- 等待调度器空闲超时：不写入任何修复结果，保持调度停止并提示用户重试。
- 重新读取时数据集不存在：停止修复并提示目标数据集已不存在。
- 数据或任务保存失败：不自动重启调度，避免在部分修复状态上继续处理。

## 测试

- 调度器忙碌时，`waitForIdle()` 必须等待执行器真正结束。
- 调度器已经空闲时，`waitForIdle()` 立即完成。
- 等待超时必须拒绝并给出明确错误。
- EPUB 修复编排必须在空闲之后重新读取数据，并使用重新读取的对象计算修复结果。
- 保存完成前不得重新启动调度器；失败时不得启动。
- 现有 EPUB 章节过滤、分段保留与补跑测试保持通过。

## 非目标

- 不引入全局数据版本协议或修改其他存储模块。
- 不自动再次操作用户当前六朝数据；代码发布后由用户重新选择原 EPUB 执行修复。
- 本次修改不自动部署或发布版本。
